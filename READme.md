Баг #1 — Тихое отравление кэша Redis (Call Service)
Почему сложный: Баг не вызывает ошибок — система молча работает, но всегда читает из БД. Никаких исключений, никаких предупреждений. Почти невозможно поймать без специального профилирования трафика Redis.Сломанный оригинальный код в call_service/main.py:
python
# Ключ "history" — без user_id!
cache_key = f"history"

# Итог: пользователь 1 и пользователь 2 получают ОДНУ и ту же запись в кэше.
# Ключ вообще не содержит информации о том, чьи это данные.
redis_client.setex(cache_key, 60, json.dumps(result))
Почему тяжело найти: Нет исключений — Redis читает и пишет успешно. Но так как все пользователи делят один ключ "history", запрос пользователя 2 перезаписывает кэш пользователя 1. Вдобавок get(cache_key) может вернуть данные чужого пользователя. Система выглядит рабочей, но отдаёт неверные данные или никогда не попадает в кэш. Для обнаружения нужно следить за Redis через команду MONITOR.Исправление: cache_key = f"history:{user_id}" — добавление user_id делает ключ кэша уникальным для каждого пользователя.





Баг #2 — Невидимая ошибка сети Docker (Call Provider → Call Service)
Почему сложный: Код выглядит абсолютно корректным в изоляции. Он ломается только внутри Docker — локально при запуске файла воспроизвести нельзя.Сломанный оригинальный код в docker-compose.yml + call_provider/main.py:
python
# call_provider/main.py — полностью игнорирует переменную окружения
CALL_SERVICE_URL = "http://localhost:8002"  # захардкожено!

# docker-compose задаёт правильную переменную:
# CALL_SERVICE_URL: http://call_service:8002
# ...но call_provider игнорирует os.getenv() и использует localhost
Почему тяжело найти: localhost внутри Docker-контейнера указывает на сам контейнер, а не на хост-машину. call_service работает в другом контейнере, поэтому localhost:8002 недоступен и возвращает 502 Bad Gateway. Разработчик должен знать о сетевой модели Docker (у каждого контейнера свой localhost) и понимать, что имена сервисов вроде call_service — это DNS-имена во внутренней сети Docker.Исправление: Использовать CALL_SERVICE_URL = os.getenv("CALL_SERVICE_URL", "http://call_service:8002") — читать правильную переменную окружения, которую задаёт Docker.





Баг #3 — Отсутствующая система JWT-авторизации (API Gateway)
Почему сложный: Это не одна пропущенная строка — это целый отсутствующий слой безопасности. В оригинале middleware делает вид, что проверяет запросы, но на деле ничего не делает. JWT требует понимания криптографии (подпись, срок жизни, структура payload), архитектуры middleware и жизненного цикла токена.Сломанный оригинальный код в api_gateway/main.py:
python
@app.middleware("http")
async def auth_middleware(request: Request, call_next):
    # Ничего не проверяет. Пропускает всё подряд.
    response = await call_next(request)
    return response
Что отсутствовало — целый модуль api_gateway/jwt_auth.py нужно было создать с нуля:
plaintext
create_token()              → подписывает payload с exp/iat/user_id/username
verify_token()              → декодирует и проверяет подпись + срок жизни
extract_token_from_header() → разбирает "Authorization: Bearer <token>"
POST /api/auth/login        → выдаёт JWT при верных учётных данных
Почему тяжело найти: Middleware существует и выполняется при каждом запросе — он просто ничего не делает. Никакой явной ошибки нет. Разработчик должен понять: (1) middleware, который вызывает call_next без проверки — это не «авторизация», а пропуск насквозь; (2) JWT требует секретного ключа, алгоритма и срока жизни; (3) эндпоинт логина должен быть исключён из проверки авторизации, иначе возникнет дедлок — токен получить невозможно, а без токена не пустят. Всё это должно работать вместе, чтобы система была безопасной.
