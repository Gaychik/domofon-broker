# Баг #1. localhost вместо Docker-имён сервисов (Проблема #3)В docker-compose.yml у call_service была переменная PROVIDER_URL: http://localhost:8003, а у call_provider — CALL_SERVICE_URL: http://localhost:8002. Внутри Docker-сети каждый контейнер имеет свой собственный localhost, поэтому localhost:8003 из контейнера call_service указывал не на call_provider, а на самого себя. Аналогично в обратную сторону. Это приводило к молчаливому провалу — httpx выбрасывал ConnectError, но она ловилась в except: pass, и система возвращала "status": "failed" без каких-либо видимых ошибок. Диагностировать это можно было только сопоставив URL-ы в docker-compose.yml с кодом сервисов и поняв, что в Docker-сети нужно использовать имена сервисов (call_provider, call_service), а не localhost.
# Баг #2. Общий ключ Redis для всех пользователей (Проблема #4)В call_service/main.py ключ кэша был задан как cache_key = f"history" — без user_id. Это значит, что все пользователи разделяли один и тот же кэш: запросив историю пользователя A, результат кэшировался, а следующий запрос истории пользователя B (если кэш ещё не истёк) возвращал данные пользователя A. Ошибка коварна тем, что при ручном тестировании с одним пользователем всё работает корректно, а проявляется только при нескольких пользователях. Дополнительно при каждом новом звонке кэш не инвалидировался, поэтому история могла быть устаревшей
# Баг #3 — Циклическая зависимость в docker-compose Файл: docker-compose.yml call_service зависел от call_provider, а call_provider — от call_service. Docker Compose выдавал: dependency cycle detected. Ни один контейнер не мог запуститься. Исправлено: убраны взаимные depends_on. Сложность: ошибка блокирует весь запуск, но в логах выглядит как непонятный cycle detected, не указывая на конкретные строки конфигурации.
